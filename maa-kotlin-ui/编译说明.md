# MAAFW-火影忍者手游——编译、维护与排查说明

最后更新：2026-08-15
基准环境：已实际编译成功（BUILD SUCCESSFUL in 8m50s）

本文是本项目唯一的编译说明。编译环境和命令以本文为准。

## 一、项目与编译环境

项目源码存放在 Android 共享存储中，实际编译时需同步到 proot/Linux 的可执行
工作区。Android SDK 同样应放在 proot/Linux 的可执行文件系统中。

SD 卡 SDK 归档：
  android-sdk/（约 447 MB）

注意：Android 共享存储通常以 `noexec` 方式挂载，二进制程序不能直接在其中运行，
因此不要直接在共享存储中构建。需要恢复 SDK 时，将归档的 `android-sdk/` 完整复制到
proot/Linux 的可执行工作区。

已验证环境：
  Java：OpenJDK 17（ARM64，proot 系统内）
  platforms;android-34
  build-tools;34.0.0
  platform-tools（adb）
  cmdline-tools（sdkmanager 12.0）

build-tools/34.0.0 中的 aapt2、aapt、aidl、zipalign、dexdump 已替换为
ARM64 可执行版本。建议将 Google 官方 x86_64 版本备份到 SDK 的独立目录中。

项目依赖仓库使用阿里云 Maven 镜像，Gradle 发行版使用阿里云镜像。
gradle.properties 中的 android.aapt2FromMavenOverride 指向 ARM64 aapt2。

## 二、从 NarutoMobile 素材到 APK 的完整流程

完整链路如下：

  NarutoMobile release
    → 下载并部署 interface.json/resource
    → 把不兼容的 MultiSwipe 改写为 MultiSwipeCustom
    → Pipeline 通过 Custom action 调用 Kotlin 注入实现
    → CMake 编译 libbridge.so/liblauncher.so
    → Gradle 打包 Kotlin、assets、预编译库和新编译的 so
    → app-debug.apk

以下命令默认先在 SD 卡源码目录更新业务资源，再把源码同步到 proot 可执行工作区编译。

### 2.1 准备 MaaFramework Android 库

首次构建或需要更新 MaaFramework 时，在项目根目录运行：

  python scripts/setup_maaframework.py

脚本会查询 `MaaXYZ/MaaFramework` 的最新稳定 Release，下载其中的 Android
ARM64 预编译包并缓存，然后自动完成以下部署：

  bin/*.so → app/src/main/jniLibs/arm64-v8a/（旧版 lib/*.so 也兼容）
  include/* → app/src/main/cpp/include/

部署完成后，脚本会将实际使用的版本写入 `.maaframework-version`。更新过程中会清理
`app/src/main/jniLibs/arm64-v8a/` 中旧的 `.so`，再部署 Release 中的预编译库。
`libbridge.so` 和 `liblauncher.so` 不应手动放入该目录；它们由本项目 CMake
在 Gradle 构建时生成并自动打包。

发布构建建议固定版本，避免上游最新版本变化影响结果：

  python scripts/setup_maaframework.py --tag v5.12.3

缓存中已经有压缩包时，可以跳过下载并重新部署。不指定版本时，脚本会选择
最近写入缓存的压缩包：

  python scripts/setup_maaframework.py --skip-download

也可以从缓存中指定版本：

  python scripts/setup_maaframework.py --skip-download --tag v5.12.3

该项目只打包 `arm64-v8a`，不要改用 x86_64 或其他平台的 Release 产物。切换
MaaFramework 版本后，应重新执行完整 APK 构建，并回归控制器初始化、截图、识别、
普通点击和自定义动作。

### 2.2 拉取 NarutoMobile 素材

进入项目源码目录后执行以下命令。

下载 NarutoMobile 最新稳定 release：

  python scripts/update_narutomobile_assets.py

脚本会选择 `duorua/narutomobile` release 中的 Windows x64 ZIP（其中包含通用业务
资源），缓存到项目根目录的 `cache/`，然后将以下内容更新到 Android assets：

  app/src/main/assets/interface.json
  app/src/main/assets/resource/

使用指定版本：

  python scripts/update_narutomobile_assets.py --tag v1.2.3

使用已下载的本地 ZIP：

  python scripts/update_narutomobile_assets.py \
    --local-zip cache/MaaAutoNaruto-win-x86_64-版本号.zip

只检查压缩包内容、不覆盖 assets：

  python scripts/update_narutomobile_assets.py --dry-run

更新脚本默认会在临时 staging 目录中调用 `convert_multiswipe.py`，转换成功后再将
`interface.json` 和 `resource/` 一并部署到 `app/src/main/assets`。无需重复运行转换器。

### 2.3 将 MultiSwipe 转换为 Android Custom action

通常无需手动执行本节。仅需重新转换当前 assets 中已有的 Pipeline 时运行：

  python scripts/convert_multiswipe.py

该脚本扫描：

  app/src/main/assets/resource/base/pipeline/

并把上游节点：

  "action": "MultiSwipe",
  "swipes": [...]

转换成：

  "action": "Custom",
  "custom_action": "MultiSwipeCustom",
  "custom_action_param": { "swipes": [...] }

这是构建前的 Pipeline 改写。原因是 MaaFramework AndroidNative controller 不支持
原生多点触控；保留 `MultiSwipe` 会在运行时被拒绝。

`convert_multiswipe.py` 默认处理项目内的
`app/src/main/assets/resource/base/pipeline/`；也可通过位置参数指定其他 Pipeline 目录。
转换结束后，检查输出中的转换数量，并确认 Pipeline 中已经没有原始
`"action": "MultiSwipe"`：

  grep -R '"action"[[:space:]]*:[[:space:]]*"MultiSwipe"' \
    app/src/main/assets/resource/base/pipeline

没有输出表示转换完成。

### 2.4 Custom action 注册与输入注入链路

Pipeline 只声明动作名称，真正的输入注入发生在 App 运行时：

1. `MaaFrameworkEngine.loadResource()` 创建 Maa resource；
2. 调用 `CustomActions.register(res)`；
3. `MaaResourceRegisterCustomAction` 注册 `MultiSwipeCustom`、`NonlinearSwipe` 等动作；
4. Pipeline 执行 `action: "Custom"` 时，MaaFramework 通过 JNA 回调
   `CustomActions.kt`；
5. `MultiSwipeCustom` 解析 `custom_action_param.swipes`，构造多指针
   `MotionEvent` 并通过系统 InputManager 注入；
6. `NonlinearSwipe` 使用 `touchDown → touchMove → touchUp` 注入单指非线性滑动，
   避开 MaaFramework 多途径点 Swipe 卡死路径。

相关文件：

  app/src/main/java/com/maafw/naruto/maa/MaaFrameworkEngine.kt
  app/src/main/java/com/maafw/naruto/maa/CustomActions.kt
  app/src/main/java/com/maafw/naruto/shizuku/InputInjector.kt
  app/src/main/java/com/maafw/naruto/third/wrappers/InputManager.java

新增 Custom action 时必须同时完成两处修改：Pipeline 中写入完全相同的
`custom_action` 名称，并在 `CustomActions.register()` 的 actions 映射中注册实现。

### 2.5 更新资源版本并同步到 proot

更新素材或 Pipeline 后，建议提升 `app/build.gradle` 中的 `versionCode`。App 会同时检查
版本号、Pipeline 数量以及 assets 与设备文件的名称和大小；任一项变化都会触发重新部署。
提升版本号可以明确标记这次资源发布，也便于确认设备运行的是新 APK。

将最新源码同步到可执行工作区，关键步骤如下：

1. 清理编译工作区中旧的 `app/src/main`；
2. 将源码目录中的整个 `app/src` 同步到编译工作区；
3. 同步 `app/build.gradle`，确保版本号和构建配置一致。

必须同步整个 `app/src/main`，因为其中同时包含 assets、Kotlin/Java、AIDL 和 native
源码。只复制 `assets` 会漏掉 Custom action 或 C/C++ 变更。

### 2.6 编译 native so 并打包 APK

确认 `JAVA_HOME` 和 `ANDROID_HOME` 分别指向可用的 JDK 17 与 Android SDK，进入
编译工作区后执行标准构建：

  ./gradlew :app:assembleDebug

一次 `assembleDebug` 会依次完成：

1. 通过 `externalNativeBuild` 调用 `app/src/main/native/CMakeLists.txt`；
2. 用 Android NDK 为 `arm64-v8a` 编译 `bridge`，生成 `libbridge.so`；
3. 编译 PIE 可执行目标 `launcher`，产物命名为 `liblauncher.so`；
4. 编译 Kotlin/Java/AIDL；
5. 将 `app/src/main/assets`、MaaFramework 预编译库和 CMake 产物合并进 APK；
6. 生成并签名 Debug APK。

不需要单独运行 `ndk-build`，也不要把旧的 `libbridge.so` 或 `liblauncher.so` 放回
`app/src/main/jniLibs/arm64-v8a/`，否则可能发生重复打包或误用旧产物。

已有完整 Gradle 缓存时可离线构建：

  ./gradlew :app:assembleDebug --offline -q 2>&1 | tail -20

缺少依赖时去掉 `--offline`，或先执行：

  ./gradlew :app:dependencies

构建成功后 APK 位于：

  app/build/outputs/apk/debug/app-debug.apk

### 2.7 检查 APK 内容并安装

确认新资源和 native 产物已经进入 APK：

  unzip -l app/build/outputs/apk/debug/app-debug.apk | \
    grep -E 'assets/(interface.json|resource/base/pipeline)|lib/arm64-v8a/lib(bridge|launcher).so'

至少应看到：

  assets/interface.json
  assets/resource/base/pipeline/...
  lib/arm64-v8a/libbridge.so
  lib/arm64-v8a/liblauncher.so

将 APK 复制到设备可访问的位置，再通过 ADB 覆盖安装：

  adb install -r <APK路径>

安装后至少回归以下项目：App 启动和资源部署、截图、普通点击、NonlinearSwipe、
MultiSwipeCustom，以及一条完整任务链。

## 三、Native/NDK 编译

`app/src/main/native/` 是当前维护中的 native 源码，不再仅供阅读。Gradle 已通过
`externalNativeBuild` 接入该目录下的 `CMakeLists.txt`，执行标准 APK 构建时会自动编译：

  bridge（C++）→ libbridge.so
  launcher（C）→ liblauncher.so

当前仅构建 `arm64-v8a`，C++ 标准为 C++17。标准命令不变：

  ./gradlew :app:assembleDebug

不需要预先运行 `ndk-build`，也不要再从发行版 0.1 APK 恢复旧的 `libbridge.so`。
`app/src/main/jniLibs/arm64-v8a/` 只保留 MaaFramework 及其依赖等预编译库；
`libbridge.so` 和 `liblauncher.so` 由 CMake 在构建目录中生成并由 Android Gradle Plugin
自动合并进 APK。不要在 `jniLibs` 中同时放置这两个同名文件，否则会产生重复 native
库或误打包旧产物的问题。

当前 native 配置入口：
  app/build.gradle
  app/src/main/native/CMakeLists.txt

`Android.mk` 和 `Application.mk` 可用于独立的 AIDE/ndk-build 场景，但不是标准 Gradle
构建链。若修改 native 源码，应至少重新执行一次完整 APK 构建，不要复用旧 `.so`。

MaaFramework 相关 `.so` 仍为预编译依赖，位于：
  app/src/main/jniLibs/arm64-v8a/

## 四、MaaFramework 已知红线

1. 不要注册 MaaTaskerAddContextSink 的 focus 监听。
   在 v5.12.3/v5.13.0-beta.2 中，节点事件回调曾导致引擎随机崩溃或卡死。

2. 不要使用 MaaFramework Swipe 的多途径点形式（end 数组配 duration 数组）。
   NonlinearSwipe 已改为引擎层直接注入，见 CustomActions.kt。

3. 不要在 CustomRecognition 中通过 MaaContextRunRecognitionDirect 嵌套 OCR。
   已验证会死锁；point_race_challenge 已改用原生 OCR。

4. CustomAction 阶段拿不到 image，不能在动作阶段执行 OCR。

更完整的历史分析见：滑动卡死问题修复报告.md

## 五、资源部署与测试

资源目录：
  app/src/main/assets/resource/base/

App 启动后，资源会部署到应用专属外部存储目录下的 `resource/base`。

AssetResourceDeployer 使用 .maafw_version 校验资源版本。修改 assets 资源后，应提升
app/build.gradle 中的 versionCode，以强制重新部署；否则设备上可能继续使用旧资源。

安装 APK：
  adb install -r <APK路径>

若新版本安装后异常，可确认安装的是 app-debug.apk，并在必要时卸载旧版本后重装。

## 七、日志与排查

导出的日志位于共享存储中的 `MaaFw日志` 目录。

引擎实时日志位于应用专属外部存储目录下的 `maa_logs/maafw.log`。

任务卡住时，先查看 maafw.log 末尾最后一个 Node、Action 或 Recognition 事件，
定位卡住节点，再对照本文“已知红线”排查。
